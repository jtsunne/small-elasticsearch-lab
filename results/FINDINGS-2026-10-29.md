## Page 2: security behind Caddy

**Caddy abort over HTTP/2.** Caddy's `abort` closes an HTTP/2 stream with a reset. curl reports it as exit 92 (a stream reset), not as 52 (empty reply), which is what the same `abort` gives over HTTP/1.1. The absolute-form request line `GET http://es01:9200/_cluster/settings` is also rejected over HTTP/2 with exit 92 and never reaches the node. Evidence: `es-single-07`, `-08`, `-65` in `2026-10-29-es-single.tap`; `os-single-17`, `-18`; `es-single-kibana-79`, `-80`; `os-single-dashboards-64`. Contradicted the runner's assumption (52, 55, 56 only), not the Caddyfile. For the page: a client outside the allowlist sees a connection or stream reset, with no HTTP status.

**The `route` block and the raw-URI matchers hold.** Every non-allowlisted request was aborted, and every admin, encoded, case, dot-segment, double-slash, comma, wildcard, `_all`, date-math, `_msearch`, async search, point-in-time, scroll, `DELETE` and `GET /` variant got 404 from Caddy on both engines. Evidence: rows `L-P1` and `L-P4` to `L-P10`, `L-P17` to `L-P20` in `2026-10-29-es-single.tap`, `2026-10-29-os-single.tap` and the others. Confirmed the plan (correction 1 in plan 0.1). The demonstration that the old top-level `abort` Caddyfile proxies anyway is not part of this run.

**The role stops what the proxy passes.** `POST /app-a/_bulk` with an item naming `secret` passes Caddy; Elasticsearch answers a per-item 403 inside a 200 response, and so does OpenSearch. Evidence: `es-single-56`, `os-single-13` (direct), `os-single-44` (through Caddy). A scripted or heavy query passes every layer (`es-single-61`, `os-single-45`); a 21 MB body gets 413 (`es-single-62`, `os-single-46`); `X-HTTP-Method-Override: DELETE` has no effect (`es-single-63`, `-64`). Confirmed the plan: the allowlist is a speed bump, roles are the access control.

**`create_doc` rejects the bulk `index` action** (Elasticsearch 9.5.5). With only `read` and `create_doc` on `app-*`, a bulk `create` item gets 201 and a bulk `index` item gets 403, with or without `_id`:

```
action [indices:data/write/index:op_type/index] is unauthorized ... this action is granted by the index privileges [create,index,write,all]
```

Evidence: `es-single-57` (two `create` items, both 201) and `es-single-83` (`create` 201, `index` 403 with `op_type/index` in the reason) in `2026-10-29-es-single.tap`; the same in `es-single-kibana-90` and `es-three-local-30`. By hand, not as rows: `POST /app-a/_doc` without an id 201, `PUT /app-a/_doc/<id>` 403, `_create/<id>` on an existing id 409. Contradicted the earlier expectation that `create_doc` covers any write without an id. For the page: a client whose bulk helper sends `index` by default must send `create`; granting `index` or `write` also allows overwriting by id.

**`create_doc` does not create indices.** A bulk `create` into `app-new`, which matches `app-*` but does not exist, gets a per-item 403. Evidence: `es-single-60`. Confirmed the hypothesis.

**The application API key.** Created by `elastic` with `role_descriptors` and an expiration: it authenticates as `api_key` named `app-x-key` owned by `elastic`, carries exactly the `app_x_key` descriptor and an expiration, and neither `app_x` nor the key can create another key (403 `security_exception`). Evidence: `es-single-79` to `-82`. Confirmed the hypotheses.

**Port 9200 is not published.** From the host, `127.0.0.1:9200` is refused, and on three nodes 9300 too. Evidence: `es-single-06`, `es-three-local-14`, `-15`. Partial L-N1 only; the ufw variant was not run.

**Kibana's console bypasses the Caddy allowlist.** Kibana 9.5.5 talks to Elasticsearch directly with the logged-in user's credentials. Through `POST /api/console/proxy?path=_cluster/settings&method=GET`, `elastic` got 200 with the cluster settings (body contains `persistent`), although Caddy answers 404 for `/_cluster/settings` on the Elasticsearch site; `app_x` was refused with 401 or 403 (the TAP does not record which). Evidence: `es-single-kibana-83`, `-84`, `-14` in `2026-10-29-es-single-kibana.tap`. The plan expected the bypass; this run shows it. For the page: whoever can reach the Kibana site and log in gets every Elasticsearch API their role allows.

**The console proxy is an internal route in Kibana 9.5.5.** Without the header `x-elastic-internal-origin` Kibana answers:

```
400 uri [/api/console/proxy] with method [post] exists but is not available with the current configuration
```

With the header (any value; Kibana's own browser client sends `x-elastic-internal-origin: Kibana`) the request goes through. The header is not a security boundary. Evidence: `es-single-kibana-91` (400), `-83` (200); the route's internal default and `server.restrictInternalApis` were read from the Kibana v9.5.5 source. Contradicted the row's original expectation.

**OpenSearch Dashboards behaves the same way, without the header.** Through Dashboards 3.9.0's console proxy with `osd-xsrf: true` and basic auth, `admin` got 200 with the cluster settings and `app_x` got 403. Evidence: `os-single-dashboards-69`, `-70`. Confirmed the hypothesis. Goes on page 2 next to the Kibana finding, and on page 4 as a difference.

**Kibana starting up.** `/api/status` without credentials answers 200 with `available` in the body once Kibana is ready; `/login` 200 for an allowlisted client; both aborted for others. Evidence: `es-single-kibana-79` to `-82`. Dashboards differs, see page 4.

## Page 3: one node or three

**Readiness after `compose up --wait` is not readiness for requests.** On three nodes, `compose up --wait` reported every node healthy while the `.security-7` primary was still unassigned. A single `_cluster/health?wait_for_status=green` as `elastic` then failed with:

```
503 unavailable_shards_exception: at least one primary shard for the index [.security-7] is unavailable
authentication_processing_error: failed to retrieve password hash for reserved user [elastic]
```

Evidence: the first run of `es-three-local` (setup step and rows `-01` to `-13`); not kept in `results/`. In the second run, with a wait that retries 503, 401, 408 and no answer, all 30 rows passed (`2026-10-29-es-three-local.tap`). Not anticipated by the plan. For the page: health and setup scripts must retry 503 and 401 for a while after start, because the healthcheck in the official compose file only proves that the node answers HTTP.

**Kibana's indices make a fresh single node yellow for a moment.** Right after start, while Kibana was creating its system indices, `GET /_cluster/health` showed 35 active primaries, one primary unassigned and status yellow; every later row passed. Evidence: `es-single-kibana-01` in `2026-10-29-es-single-kibana.tap`. Transient. The row now waits with `wait_for_status=green&timeout=60s`, which has not been run yet. Belongs on page 3 next to the readiness finding, and as a note on page 2 where Kibana is added.

**Formation.** es01 to es03 with `cpus: 1` and `mem_limit: 2g` each: one cluster, roles exactly `data`, `ingest`, `master` (set as one comma-separated environment variable), a voting configuration of three, an elected master, transport TLS on everywhere with `verification_mode: certificate`, `app-a` and `secret` with copies on two different nodes, heap 1 GiB and one allocated processor on each node. Evidence: `es-three-local-01` to `-13` in `2026-10-29-es-three-local.tap`; recorded bodies `es-three-local-05.json` (coordination metadata, three node ids in `last_committed_config`), `-08.json` (certificates), `-13.json` (shard placement). Confirmed the hypotheses, including the field name `last_committed_config`.

**Startup load.** Starting three 1-CPU nodes held the laptop at about 70% CPU. A coordinator observation during the run, not a recorded measurement; do not quote it as a number on the page.

**L-T1: the elected master stops.** A new master was seen at the first poll after `docker compose stop` returned (0 s); health right after the loss was yellow with 2 nodes and 3 or 4 unassigned shards; six searches through Caddy in a row all got 200; a bulk create through Caddy was accepted; green again on two nodes 48 to 50 s later in three runs. Evidence: checks 4 to 7 of `2026-10-29-es-three-local-fault.tap`. Confirmed the plan. Caveat for the page: the 48 to 50 s clock starts after the six searches and the bulk write, not at the stop, so the time from losing the node to green is longer and was not measured. It is consistent with `index.unassigned.node_left.delayed_timeout` of 1 minute (FROM TRAINING), not a measurement of it; the TAP diagnostic's wording "after the master change" overstates where the clock starts. That Caddy retried on another node is the likely mechanism, but Caddy's logs were not recorded.

**L-T2: a second node stops, no master.** The last node reports no master within a second. `_cluster/health` answers:

```
503 master_not_discovered_exception
```

A search through Caddy still answers 200 with hits, served by the last node from its local shard copy (`_shards.total` 1, successful 1); with `cluster.no_master_block` at its default `write` this is a read of possibly stale data. A bulk create is held by Elasticsearch for about 60 s and then rejected:

```
503 cluster_block_exception: blocked by: [SERVICE_UNAVAILABLE/2/no master];
```

(curl exit 0, `time_total` 60.0 s, client timeout 100 s.) With a 30 s client timeout the client sees nothing at all: curl exit 28, status 000, 0 bytes after 30.0 s. Evidence: checks 8 to 10 of `2026-10-29-es-three-local-fault.tap` (the 100 s run); the 30 s run passed the same checks the same day and its TAP was not kept in `results/`. This settled an open question from the first run, which had seen "no HTTP response": hypothesis (a), Elasticsearch holds the write past the client timeout, was right; hypothesis (b), Caddy drops the connection, was wrong. For the page: without a master, reads keep working and writes hang for a minute before a 503; an application with a shorter timeout only sees timeouts and never the reason.

**Recovery.** With both nodes started again: green with three nodes 48 to 50 s after the start, the write accepted during L-T1 present, the write blocked during L-T2 absent, one `cluster_uuid` on all three nodes. Evidence: checks 11 to 15 of the fault TAP. Confirmed the plan.

**Procedure A, `es-grow-restore` (L-G1), second batch.** Steps 0 to 5 ran once in runbook order (including the rehearsal restore of `grow-1`, then `--final` and `grow-final --replace`), each exiting 0; the end-state checks passed 22 of 22 rows with `COMPOSE_PROFILES=new NODE_SERVICE=es01`. ## Page 1: sizing

**Heap, explicit mode.** With `-Xms1g -Xmx1g` in a 2 GiB container the heap max is 1073741824 bytes on Elasticsearch (one node and each of three) and on OpenSearch. Evidence: `es-single-02`, `es-single-78` (recorded `input_arguments`, `2026-10-29-es-single/es-single-78.json`), `es-single-kibana-02`, `es-three-local-09`, `os-single-09`. Confirmed.

**Heap, auto-sizing mode (L-M1), second batch.** `es-single` with `ES_HEAP_OPTS=` empty passed 83 of 83 rows; the node reported `heap_max_in_bytes` 1073741824 and `input_arguments` `-Xms1024m -Xmx1024m`, set by Elasticsearch itself, where the explicit run shows `-Xms1g -Xmx1g`. All other JVM arguments are identical in the two modes, including `-XX:MaxDirectMemorySize=536870912` (512 MiB, half the heap). Evidence: `2026-10-29-es-single-autoheap.tap` (rows `es-single-02`, `-78`), body `2026-10-29-es-single-autoheap/es-single-78.json`; compare `2026-10-29-es-single/es-single-78.json`. Confirmed the hypothesis: Elasticsearch 9.5.5 picks 1 GiB, half of a 2 GiB container, by itself. One container size only; the 40% rule below 1 GiB of heap was not exercised.

**Processors under `cpus: 1`.** Elasticsearch 9.5.5 reports `allocated_processors` 1, write thread pool 1, search thread pool 2; OpenSearch 3.9.0 reports `allocated_processors` 1. Evidence: `es-single-03`, `-04`, `es-three-local-10`, `os-single-10`. Resolved plan 0.1 item 7 (UNCERTAIN) for this host: the cgroup CPU quota is honoured and `node.processors` does not need to be set. Measured on cgroup v2 only.

**System shards (snapshot, not settled).** On a fresh `es-single` right after setup: 5 shards, of which 3 are system (`.security-7`, ILM history, deprecation log data stream). With Kibana, recorded while Kibana was still starting (one shard initializing): 36 shards, 34 of them not `app-a` or `secret`, and 53 indices including hidden ones. Evidence: `es-single-05` (`2026-10-29-es-single/es-single-05.json`), `es-single-kibana-05`, `-78`. L-S1 asks for a settled number with and without Kibana; this is a first indication only, since the Kibana count was taken before startup finished.

**L-M2: 1536 MiB of heap in a 2 GiB container under bulk load, second batch.** The same load twice into a single node (`scenarios/bad-heap` with `compose.bench.yaml`: `cpus: 1`, pinned to one host CPU, `mem_limit: 2g`, security on, memory lock on), once with `-Xms1536m -Xmx1536m` (`bad`) and once with `-Xms1g -Xmx1g` (`control`): 3,000,000 synthetic documents into index `lm2`, generated by awk with seed 42, 2,008,963,499 source bytes (669.7 bytes per document on average: 2,008,963,499 / 3,000,000), dynamic mapping, bulk size 1000, 2 clients, default 1 s refresh. Memory sampled every 10 s from the container's cgroup v2 `memory.stat` (`anon`, `file`) and `memory.events`. Evidence: `bench/results/2026-10-29-laptop-6c16g-nvme-01-es-9.5.5-lm2/` (`run.txt` lists the files).

| | bad (1536 MiB heap) | control (1 GiB heap) |
|---|---|---|
| heap reported | 1610612736 bytes | 1073741824 bytes |
| wall time | 250.0 s | 159.9 s |
| docs/s | 11,998 | 18,764 |
| bulk p50 / p90 / p99 / max | 122.6 / 218.5 / 1,194 / 6,468 ms | 88.3 / 179.7 / 260.9 / 1,117 ms |
| failed requests, 429, retries | 0, 0, 0 | 0, 0, 0 |
| `OOMKilled`, restarts, `oom_kill` | false, 0, 0 | false, 0, 0 |
| `anon` max | 2012.5 MiB (first sample, as the load started) | 1517.2 MiB |
| `file` max | 174.3 MiB | 618.6 MiB |
| `max` events (limit reached) | 72,644 | 18,949 |
| store after the load | 1.29 GiB (1,388,029,508 bytes) | 1.29 GiB (1,388,325,044 bytes) |

Arithmetic: throughput 11,998 / 18,764 = 0.639, so 36.1% lower; wall time 250.0 / 159.9 = 1.56; p99 1,194.0 / 260.9 = 4.58; max 6,467.6 / 1,116.7 = 5.79; p50 1.39, p90 1.22; limit events 72,644 / 18,949 = 3.83 (291 per second of load against 119). MiB values are bytes / 1,048,576 from the monitor files; the limit is 2,048 MiB. The bad run's last 30 container log lines contain young GC pauses of 1.5 s and 2.6 s, `[gc][...] overhead, spent [2.6s] collecting in the last [2.9s]`, and the GC monitor's own periodic task taking 5.2 s and 6.2 s (`took [6201ms] which is above the warn threshold of [5000ms]`); the control run's last 30 lines contain none (only the tail was kept, so this is not a full comparison).

Observed: hypothesis 1, an OOM kill, did not happen for this load (refuted for bulk ingest at this size). Hypothesis 2, survival with memory pressure, did: about 36% lower ingest throughput and 4.6 times the p99 bulk latency of the 1 GiB heap, more limit events, less `file` memory, and long young GC pauses.

Caveat that changes how the memory columns read: the node's data directory was on the host's `/tmp`, a tmpfs (`run.txt`, `host.txt`). The index files therefore lived in RAM and were charged to the container's own memory cgroup, where `memory.stat` counts tmpfs pages under `file` (FROM TRAINING, kernel cgroup v2 documentation). In both runs `anon` plus `file` peaked at about 2,031 to 2,033 MiB of the 2,048 MiB limit, and the 1.29 GiB index never fitted beside the heap; the rest was presumably swapped out (HYPOTHESIS: `shmem` and swap were not sampled; the host swaps to zram first). So `file` here is "index data still in RAM", not page cache over a disk, and this run cannot separate cache starvation from GC pressure. Throughput, latency, the GC pauses and the absence of an OOM kill stand as observed under these conditions. `bench/l-m2.sh` now refuses tmpfs and samples `shmem` and swap; rerun it on a disk before the sizing page explains the mechanism. Only ingest ran; the query side of L-M2 is open. For the page: on this run, the oversized heap cost throughput and tail latency without crashing; "it will be OOM-killed" is not what happens first.

**L-M3: off-heap memory, partial.** With the heap pre-touched and locked (`-XX:+AlwaysPreTouch` is in the recorded JVM arguments, `bootstrap.memory_lock` is on), `anon` minus heap estimates the JVM's memory outside the heap. Control under bulk load: 1,517.2 - 1,024 = 493 MiB at its peak. Bad, at its first sample as the load started: 2,012.5 - 1,536 = 476.5 MiB. Both fall inside the 300 to 600 MiB estimate that was FROM TRAINING. Caveats: one host, one load type (bulk ingest, no queries), two runs; `anon` includes more than the JVM process in principle (anything else in the container), and the tmpfs caveat above does not affect `anon`. `MaxDirectMemorySize` is 512 MiB with a 1 GiB heap (auto run above), so direct buffers alone could reach that under other loads. ## Page 4: OpenSearch

**Content-Type is enforced.** A request body without `Content-Type` (curl's `--data-binary` then sends `application/x-www-form-urlencoded`) gets:

```
406 Content-Type header [application/x-www-form-urlencoded] is not supported
```

Elasticsearch accepted the same requests in this lab. Evidence: first run, `os-single-01`, `-02`, `-12`, `-13`, `-15`, `-44`, `-45`; second run, with explicit types, all pass (`2026-10-29-os-single.tap`). Contradicted the rows, not a documented expectation. For the page: scripts that work against Elasticsearch can fail against OpenSearch on this alone.

**Security plugin with its own configuration.** With the demo installer off and the scenario's own users, roles and certificates: no anonymous access (401 on `/`), `admin` has `all_access`, and `admin:admin`, `kibanaserver:kibanaserver` and `readall:readall` are rejected. Evidence: `os-single-03` to `-07`. Confirmed L-O2.

**`app_writer` and the bulk `index` action.** The OpenSearch role grants `indices:data/write/index` on `app-*`, so a bulk `index` item without `_id` is accepted (`errors: false`), and it was the first document in `app-a`, so the role is sufficient for a bulk write that adds a dynamic mapping. An `index` item naming `secret` gets a per-item 403, at the node and through Caddy; reading `secret`, creating `app-b` and deleting `app-a` get 403. Evidence: `os-single-12`, `-13`, `-44`, `-14` to `-16`. Confirmed L-O3. Not tested: a create-only OpenSearch role equivalent to Elasticsearch's `create_doc`, so the two engines' roles in this lab are not equivalent; `indices:data/write/index` very likely also allows overwriting by id, which was not tested.

**Dashboards `/api/status` needs authentication.** With the security plugin, `/api/status` answers 401 without credentials, 200 for `admin`, and 401 for `kibanaserver:kibanaserver`. Evidence: `os-single-dashboards-66` to `-68`. Kibana 9.5.5 answers 200 without credentials (`es-single-kibana-81`).

**Dashboards with 1 GiB.** Dashboards 3.9.0 started and answered every row with `mem_limit: 1g` and a 640 MB V8 heap. Memory headroom, `OOMKilled` and startup time were not recorded, so "1 GiB is enough" is not established.

**Heap and processors.** See page 1: 1 GiB heap (set explicitly; OpenSearch does not size from the container), one allocated processor.
